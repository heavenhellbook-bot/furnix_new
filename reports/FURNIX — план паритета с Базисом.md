# FURNIX — план паритета с Базисом

**Дата:** 3 ноября 2026 года
**Основа:** `reports/Базис-Мебельщик — возможности и промт для FURNIX.md`, README.md, ROADMAP.md, `reports/FURNIX — полный обзор и история проекта.md`, исходный код (`assembly-editor.js`, `index.html`).
**Цель:** FURNIX должен заменить Базис в процессе «SketchUp → FURNIX → раскрой, закупки, 1С». Повторяется только функциональность, своими решениями. Код, форматы файлов, интерфейс, названия и тексты Базиса не копируются.

Статусы в таблице:
- **есть** — работает в прототипе;
- **частично** — есть упрощённая или неполная версия, не пригодная для производства без доработки;
- **нет** — функции нет.

Все функции, на которые ссылается таблица, находятся в `assembly-editor.js`, если не указано иное. Встроенный код прототипа v0.2 (`packSheets`, `makeCutSVG`, `drawingSVG`) удалён из `index.html` в ноябре 2026 года.

## 2. Группы недостающего

### MVP — без этого FURNIX нельзя использовать на производстве вместо Базиса
1. Проверка размера панели против размера плиты (постоянная, в проекте).
2. Кромка по материалам с уменьшением размера детали «в распил».
3. Правила крепежа нашего производства и автоматическая присадка (модель отверстий).
4. Рабочие чертежи деталей с координатами отверстий, кромкой и текстурой.
5. Базовый гильотинный раскрой с картами, статистикой и бирками.
6. Смета по базе материалов и цен: плиты, кромка, фурнитура, операции.
7. Спецификация с экспортом в XML для 1С.

Порядок выбран по зависимостям. Кромка меняет размеры для раскроя и сметы. Присадка нужна чертежам и смете. Раскрой даёт метраж резов для сметы. XML для 1С собирает итог из всех предыдущих задач.

### Этап 2
- Параметрические мастера: шкаф, шкаф-купе, тумба, кухонный модуль (с панелью жёсткости, штангами, монтажными планками).
- Ящики по описанной конструкции и системе выдвижения (с дном и расчётом деталей по направляющей).
- Двери-купе и рамочные двери; накладные, полунакладные и вкладные фасады с настраиваемыми зазорами.
- Полезные обрезки как отдельная база с режимом текущих обрезков и ручным вводом деталей в раскрой.
- Импорт OBJ (техника, декор, фурнитура как визуальные объекты).
- Фотореалистичный рендер с текстурами декоров.
- Сопутствующее: фиксированные виды спереди, слева и сверху; история действий с отменой; замена типа крепежа во всём изделии; панели произвольного контура и вырезы.

### Позже
- ЧПУ и постпроцессоры станков (присадка, фрезеровка, пильные центры), симулятор.
- Нестинг.
- Интерьер помещения и салон (стены, проёмы, каталог, оформление заказа).
- Упаковка и комплектовка.
- Склад (остатки плит, кромки, фурнитуры между проектами).
- AR, облако, личный кабинет.
- Обмен корпусами с фурнитурой поставщиков (после выбора поставщика и получения прав на данные).

## 3. Задачи MVP

Общие правила для всех задач:
- Размеры в миллиметрах.
- Новые данные — необязательные поля JSON v4. Старые проекты открываются со значениями по умолчанию, которые нельзя молча считать производственными.
- Каждую задачу проверяют новые случаи в `runSelfChecks()` (кнопка «Проверить проект») и ручной сценарий в README. Тест-раннера в проекте нет, и ставить его только ради этого не планируется.
- Значения нашего производства (размеры плит, пропил, правила кромки и крепежа, цены, формат 1С) не придумываются. До получения ответов они отмечаются как незаданные (см. раздел 4).

### MVP-1. Проверка размера панели против размера плиты — S
- **Что делаем.** Добавляем постоянную проверку в `validateProject`. Деталь с учётом текстуры, кромки (после MVP-2), припуска по периметру листа и габаритов станка должна помещаться на лист своего материала и толщины. Нарушение показывается в замечаниях проекта и в дереве, а не только при расчёте раскроя. Учитываются собственные размеры листа материала (`sheetWidth` / `sheetLength`) или выбранный формат листа.
- **Файлы.** `assembly-editor.js` (`validateProject`, общая функция проверки, которую переиспользует `optimizeCutPlan`), `README.md`.
- **Данные.** Формат не меняется; используются существующие `materials[].sheetWidth/sheetLength`, `cutSettings.trim`, `machineWidth/machineLength`, `grain`.
- **Проверка.** Самопроверки для четырёх случаев: деталь 2200×600 на листе 2800×2070 (направленная текстура — помещается), деталь 2900×600 (не помещается), деталь без текстуры в повороте и деталь, превышающая габарит станка. Вручную: задать ширину корпуса 3000 мм — замечание появляется сразу, раскрой выдаёт то же сообщение.

### MVP-2. Кромка по материалам и размер «в распил» — M
- **Что делаем.**
  - Добавляем каталог кромок: код, название, толщина, ширина, цена за погонный метр.
  - Добавляем назначение кромки на каждый из четырёх торцов детали.
  - Добавляем правила по умолчанию для генерируемых деталей (кто облицовывается и чем); правила будут заданы по ответам из раздела 4.
  - Считаем размер «в распил»: чистовой размер минус толщина кромки и, если так принято на производстве, плюс припуск на фуговку.
  - В интерфейсе и выгрузках показываем оба размера: чистовой и «в распил».
  - Раскрой и проверка MVP-1 используют размер «в распил».
  - Считаем метраж кромки по материалам.
  - CSV ViyarPro остаётся с чистовыми размерами: ВИЯР пересчитывает их сам, это нужно подтвердить контрольным импортом.
- **Файлы.** `assembly-editor.js`:
  - `addGeneratedPart`, `partEdgeLabel`;
  - редактор детали в `buildEditor`;
  - `specificationRows`, `optimizeCutPlan`, `partsDrawingSvg`, `dxfDocument`;
  - загрузка JSON, `validResourceBundle`;
  - `README.md`.
- **Данные (JSON v4, необязательные поля).**
  - `resources.edgeMaterials: [{ code, name, thickness, width, unit: "м", price, currency, supplier, priceSource, priceDate, priceValidUntil, priceStatus }]`
  - `resources.edgeRules: { generated: { <тип детали>: [код|null ×4] }, jointingAllowance: число|null }`
  - у детали — `edgeBands: [код|null, код|null, код|null, код|null]` (L1, L2, W1, W2)

  Старые `edges: [bool ×4]` при открытии превращаются в назначение «кромка по умолчанию, не подтверждена».
- **Проверка.**
  - Самопроверки: деталь 720×560 (длина × ширина) с кромкой 2 мм по L1 (вдоль длины) и 0,4 мм по W1 (вдоль ширины) даёт размер «в распил» 719,6×558 мм (без припуска на фуговку).
  - Метраж кромки совпадает с суммой длин облицованных торцов.
  - Старый JSON открывается и не меняет размеры, пока правила не заданы.
  - Вручную сверить выгрузку с расчётом на трёх деталях.

### MVP-3. Правила крепежа и автоматическая присадка — L
- **Что делаем.**
  - Вводим модель отверстия: деталь, грань (пласть A/B, торец L1/L2/W1/W2), координаты X/Y в системе детали, диаметр, глубина или «насквозь», тип операции, ссылка на компонент и правило.
  - Вводим правила производства для конфирмата, шканта, эксцентриковой стяжки и полкодержателя. Правило задаёт:
    - отступы от торцов, шаг или количество по длине шва;
    - для каждой из двух деталей соединения — диаметр и глубину на пласти и на торце.
  - Для всех соединений корпуса (боковина — дно, крыша, полка, перегородка) крепёж и отверстия рассчитываются автоматически, с учётом поворотов (через существующие функции преобразования координат).
  - Нужна команда «Заменить тип крепежа во всём изделии».
  - Нужны проверки:
    - отверстие попадает в тело детали;
    - глубина не превышает толщину;
    - отверстия не конфликтуют по минимальному расстоянию;
    - отверстие в торце помещается по толщине.
  - Текущее эскизное соединение (`connectionPositions`) становится частным случаем правила.
- **Файлы.** `assembly-editor.js`:
  - `findJoint`, `connectionPositions`, `createConfirmatComponents`, `validHardwareComponent`;
  - новые функции правил и отверстий;
  - `renderModel` / `addFastener` (отображение отверстий);
  - `validateProject`, загрузка JSON;
  - `README.md`, `ROADMAP.md` (закрыть пункты Priority 2 по мере выполнения).
- **Данные (JSON v4, необязательные поля).**
  - `resources.fasteningRules: [{ id, type, name, edgeOffset, pitch|null, count|null, minCount, holes: { partA: {face, diameter, depth}, partB: {face, diameter, depth} }, source, status }]`
  - у соединения — `ruleId`

  Отверстия рассчитываются из правил и в проекте не хранятся. В снимок сметы и в выгрузки они попадают как рассчитанный результат.
- **Проверка.**
  - Самопроверки: для корпуса 800×720×560 при заданном правиле (шаг, отступ) число и координаты отверстий совпадают с ручным расчётом.
  - При повороте 0/90/180/270° локальные координаты отверстий не меняются.
  - Отверстие глубже толщины детали даёт замечание.
  - Вручную сверить с контрольной деталью на производстве.

### MVP-4. Рабочие чертежи деталей с координатами отверстий — M
- **Что делаем.** Чертёж на каждую деталь, в собственном оформлении:
  - контур в масштабе;
  - чистовые размеры и размеры «в распил»;
  - кромка по торцам с обозначением материала;
  - стрелка направления текстуры;
  - отверстия на пласти и на торцах (диаметр, глубина), таблица координат от базового угла и размерные цепочки;
  - штамп: изделие, деталь, материал, толщина, количество, номер детали из раскроя;
  - выгрузка SVG (по детали и общим листом) и PDF через печать браузера.

  Нужна отдельная настройка: от какого угла отсчитывать координаты и как обозначать пласти (раздел 4).
- **Файлы.** `assembly-editor.js` (`partsDrawingSvg` заменяется новым построителем, `dxfDocument` дополняется слоем отверстий), `README.md`.
- **Данные.** Формат проекта не меняется; чертежи строятся из модели, кромки (MVP-2) и отверстий (MVP-3).
- **Проверка.**
  - Самопроверки: координаты в таблице совпадают с моделью отверстий, на чертеже столько же отверстий, сколько в модели.
  - Вручную: распечатать чертёж боковины и сверить рулеткой с изготовленной деталью.

### MVP-5. Гильотинный раскрой с картами, статистикой и бирками — L
- **Что делаем.**
  - Раскрой строим по полосам: плита → полосы → детали, только сквозные резы.
  - Сравниваем несколько вариантов (поперечные и продольные полосы, разные сортировки) и выбираем лучший по понятным критериям: число листов, отходы, затем длина резов.
  - Учитываем текстуру, пропил, припуск, остатки и размер «в распил».
  - Статистика по материалу: листов, остатков, процент отходов, длина резов.
  - Карта: SVG/печать с номерами деталей и порядком резов.
  - Бирки: наклейка на деталь (заказ, изделие, деталь, размер, кромки, материал, номер на карте) со штрих-кодом. Штрих-код рисуем своей реализацией без внешних сервисов.
  - Выгрузка карт и списка резов в CSV.
- **Файлы.** `assembly-editor.js` (`optimizeCutPlan` разделяется на построитель полос и выбор варианта, `renderCutPlan`, новые построители карты и бирок), `README.md`.
- **Данные.**
  - `resources.cutSettings` дополняется необязательными полями: `firstCutDirection`, `optimizationOrder`, `labelSize`.
  - Результат раскроя — `cutPlan: { variant, sheets: [{ strips: [{ cuts }], placements }], stats }` в снимке сметы.
  - Номер детали на карте — стабильный идентификатор для бирки и чертежа.
- **Проверка.**
  - Самопроверки: все резы сквозные (каждая деталь лежит в своей полосе, полосы не пересекаются).
  - Сумма площадей деталей, остатков и отходов равна площади листа.
  - Текстура соблюдается; отсутствие деталей и деталь больше листа обрабатываются.
  - Вручную: сравнить число листов и отходы с текущим раскроем производства на одном реальном заказе; напечатать бирки на принтере производства.

### MVP-6. Смета по базе материалов и цен — M
- **Что делаем.** Расширяем `makeEstimate`:
  - плиты: целые листы и, по правилу производства, использованные остатки;
  - кромка: погонные метры с запасом по правилу производства;
  - фурнитура и крепёж: штуки по модели MVP-3;
  - операции: распил (метры резов из MVP-5), кромкование (метры), присадка (отверстия), сборка (по правилу);
  - наценка и накладные расходы.

  Каждая строка хранит цену, источник, дату и срок. Строки без цены явно исключаются из суммы. Старые версии смет не меняются.
- **Файлы.** `assembly-editor.js` (`makeEstimate`, `validEstimate`, `renderEstimateHistory`, каталог цен в форме ресурсов), `README.md`.
- **Данные (JSON v4, необязательные поля).**
  - `resources.hardwarePrices: [{ code, name, unit: "шт", price, … }]`
  - `resources.operationPrices: [{ code: "cut"|"edge"|"drill"|"assembly", unit, price, … }]`
  - `resources.pricing: { markupPercent, overheadPercent }`
  - Снимок сметы дополняется группами строк; старые снимки остаются валидными.
- **Проверка.**
  - Самопроверки: сумма по контрольному проекту с заданными ценами совпадает с ручным расчётом.
  - Просроченная цена исключается; строки без цены перечислены.
  - Вручную: сравнить с последней сметой производства на тот же заказ.

### MVP-7. Спецификация с экспортом XML для 1С — M
- **Что делаем.**
  - Выгружаем XML собственной схемы FURNIX (UTF-8, версия схемы в корне):
    - заказ и изделия;
    - детали с размерами «в распил»;
    - материалы плит (количество листов или м²);
    - кромка (м);
    - фурнитура и крепёж (шт.);
    - операции;
    - для каждой позиции — артикул или код номенклатуры 1С для сопоставления.
  - Добавляем таблицу соответствия «код FURNIX → номенклатура 1С» с ручным заполнением и предупреждением о несопоставленных позициях.
  - Загрузку на стороне 1С выбираем по ответу из раздела 4: обработка под нашу схему или стандартный формат обмена 1С. Формат Базиса не повторяем.
- **Файлы.** `assembly-editor.js` (новый построитель XML на основе `specificationRows` и данных MVP-2…6, редактор соответствий), `README.md`. При необходимости — описание схемы в `reports/`.
- **Данные (JSON v4, необязательные поля).**
  - `resources.accountingMap: [{ furnixCode, kind, accountingCode, accountingName, unit }]`
  - Выгрузка — отдельный файл `furnix-spec-<заказ>.xml`.
- **Проверка.**
  - Самопроверки: XML корректен, количества совпадают со спецификацией и сметой, несопоставленные позиции перечислены.
  - Вручную: загрузить файл в тестовую базу 1С и сверить документ спецификации.

## 5. Ограничения плана
- Оценки сложности даны для одного разработчика и текущей архитектуры (один модуль `assembly-editor.js` на браузере). Задача L может потребовать разделить модуль на файлы. Это решается внутри задачи без смены формата проекта.
- Паритет относится к функциям, а не к сертификации. Пригодность к производству подтверждается контрольными деталями и заказами на нашем производстве.
- Задачи «Этапа 2» и «Позже» здесь не детализированы. Их план составляется после MVP.
